# 사업 정의 (Business Definition)

> 이 문서가 **사업의 와꾸**다. 홈페이지의 모든 문구는 여기서 파생된다.
> 근거: 저장소 밖 비공개 역량 대장 + 개인 업무 기록 (2026-05 ~ 2026-08)
>
> 작성일: 2026-08-13 · 결정 기록: [adr/0008-business-definition.md](adr/0008-business-definition.md)

---

## 1. 한 문장

> **고객의 로봇 개발이 올라탈 시뮬레이션 파이프라인을 만든다 — 시뮬레이션에서 출발해, 개발 내내 돌아가고, 실기 배포에서 닫힌다.**

파는 것은 검증 보고서 한 건이 아니라 **개발 속도**다. 만들기 전에 답을 얻고(사전 검증),
만드는 동안 실기를 기다리지 않고 돌리고(개발 가속), 만든 뒤에 차이를 재서 되돌린다(Sim-to-Real 정합).
셋은 별개 서비스가 아니라 한 줄로 이어진 하나의 파이프라인이다.

---

## 1-1. 제공물 — 무엇을 세워 넘기는가

**이 문서에서 가장 중요한 절이다.** 이 목록이 흐려지면 사업이 다른 업으로 미끄러진다(§9).

> 개정 2026-08-14 ([adr/0010](adr/0010-deliverable-first-voice.md)) — 이 절은 원래
> "역할 경계 — 누가 무엇을 하는가"였다. 경계 자체는 유효하지만, **경계를 선언하는 형태로 쓰면
> 고객에게는 "안 해 주는 일 목록"으로 읽힌다.** 그래서 같은 내용을 **세워 넘기는 것**으로 다시 쓴다.
> 경계는 아래 산출물 목록이 스스로 말한다 — 목록에 로봇도 제어 소프트웨어도 없다.

| 세워 넘기는 것  | 내용                                                         | 고객이 얻는 것                      |
| --------------- | ------------------------------------------------------------ | ----------------------------------- |
| **가상 에셋**   | 로봇 · 설비 · 환경 모델(기구·물리 파라미터 포함)             | 실기가 없어도 대상이 존재한다       |
| **테스트베드**  | 그 에셋이 물리로 돌아가고 작업 시나리오가 그대로 실행되는 장 | 시나리오를 즉시 돌려 본다           |
| **개발 접속면** | 제어 · 인지 개발이 곧바로 붙는 인터페이스와 명령 경로        | 개발이 하드웨어 일정에서 풀린다     |
| **근거**        | 도달성 · 간섭 · 사이클 타임 · 경계값과 각 결론의 신뢰 등급   | "될 것 같다"가 아니라 숫자를 받는다 |
| **실기 정합**   | 배포 후 항목별 차이 계측과 그 값을 되먹인 모델               | 시뮬레이션을 어디까지 믿을지 안다   |

**입력으로 받아야 하는 것**(경계가 아니라 성립 조건이다): 작업 시나리오 — 무엇을 어떤 순서로
해야 하는지. 그 공정을 아는 쪽만 줄 수 있고, 우리가 지어내면 검증의 전제부터 추측이 된다.

> **우리는 로봇 엔지니어가 아니라 로봇을 아는 시뮬레이션 엔지니어다.**

이 한 줄이 양쪽 실패를 동시에 막는다.

- **로봇 개발을 대행하면** 결국 인시(人時)를 파는 일로 되돌아간다(§9-3). 위 목록에 로봇·제어
  소프트웨어가 없는 이유이며, 이것은 고객에게 선언할 문장이 아니라 **우리가 견적을 짤 때 쓰는 기준**이다.
- **로봇을 모르는 시뮬레이션 업체는** "돌아가는 그림"을 만든다. 그 그림은 실기와 대조할 수 없어서
  개발을 가속하지 못한다. 화면이 매끄러운 것과 결론이 맞는 것은 다른 일이다.

이 사업은 정확히 그 사이에 있다 — **로봇의 물리와 제어를 아는 사람이 만든 시뮬레이션 도구.**
그래서 우리가 세운 환경에서 나온 숫자는 실기의 숫자와 항목별로 맞대 볼 수 있다.

## 2. 하지 않는 일 (먼저 못박는다)

포지셔닝은 하는 일보다 **안 하는 일**로 더 분명해진다.

| 하지 않는다                          | 이유                                                                          |
| ------------------------------------ | ----------------------------------------------------------------------------- |
| **로봇 · 제어 소프트웨어 개발 대행** | 로봇을 만드는 주체는 고객이다. 우리는 그 개발이 빨라지는 환경을 만든다 (§1-1) |
| **현장 SI 파견 · 상주 인력 제공**    | 인시(人時)를 파는 일. 이 사업의 가치는 시간이 아니라 판단                     |
| 설비 제작 · 시공 · 납품              | 제조가 아니라 검증이 업이다                                                   |
| 예쁜 3D 영상 · 홍보용 애니메이션     | 결론을 만들지 않는 산출물                                                     |
| 근거 없는 "가능합니다" 답변          | §5 신뢰 등급 없이 결론을 팔지 않는다                                          |
| 학습 정책 개발 대행                  | 현재 역량 등급이 [조사] 단계다 (역량 대장 트랙 I)                             |

> **"검증 결과가 부정적"인 것도 정상 산출물이다.** "이 로봇으로는 안 된다"를 제작 전에 아는 것이 이 사업이 파는 가치다.

## 3. 왜 이 업이 성립하는가

로봇 시스템은 **만든 뒤에 문제를 발견하면 수정 비용이 폭발한다.** 그런데 현장에서 실제로 벌어지는 일은 이렇다.

- 사양서에 없는 값이 절반이다 — 링크 질량, 관성, 마찰, 그리퍼 파지력. 그런데 그 값들이 결론을 좌우한다.
- 되는 줄 알았던 자세가 **특이 자세**라 컨트롤러가 보호정지를 건다. 설치 후에 안다.
- 관절 보간으로 "직선"을 만들면 실제로는 직선이 아니다. 공차가 좁은 공정에서 문제가 된다.
- 두 축의 속도비를 맞춰 놨는데 모터 상한에 걸리면서 형상이 깨진다.
- 제어 주기가 안 나오는데 원인이 게인인지 통신인지 스케줄링인지 모른다.

이 문제들은 **전부 만들기 전에 시뮬레이션에서 드러날 수 있는 것**이다. 단, 그 시뮬레이션이 믿을 만할 때만.

그리고 문제를 늦게 아는 것보다 더 자주 벌어지는 일이 있다 — **개발이 하드웨어 일정에 묶인다.**
실기가 없으면 제어도 인지도 손을 놓고, 실기가 오면 한 대를 여럿이 나눠 쓴다. 밤에 돌릴 수도 없다.
돌려 볼 수 있는 환경이 개발 시작과 함께 있으면 그 대기가 사라진다.

**그래서 이 사업이 파는 것은 시뮬레이션 자체가 아니다.**
① "그 시뮬레이션을 어디까지 믿어도 되는가"에 대한 답과, ② 그 답을 **개발 내내 즉시 얻을 수 있는 환경**이다.
전자만 있으면 보고서 용역이고, 후자만 있으면 돌아가는 그림이다.

## 4. 핵심 루프

```
        ┌──────────────────────────────────────────────┐
        │                                              │
   [문제 정의] → [모델 구성] → [시뮬레이션] → [검증] → [실기 배포]
        ▲                                              │
        │                                              ▼
        └────────────── [차이 계측 · 모델 갱신] ←───────┘
```

- 화살표가 **되돌아온다.** 이것이 일반 시뮬레이션 용역과의 구조적 차이다.
- 한 바퀴 돌 때마다 모델의 신뢰 등급(§5)이 올라간다. **추정값이 실측값으로 바뀌는 것**이 진척이다.
- 고객은 어느 지점에서든 들어올 수 있다. 설계 단계면 왼쪽부터, 이미 실기가 있으면 오른쪽부터.

## 5. 차별점 — 이 셋이 전부다

셋 모두 **로봇을 아는 사람이 시뮬레이션을 만들 때만** 나온다(§1-1).
어떤 값이 결론을 좌우하는지, 어떤 자세가 구조적으로 위험한지, 무엇을 재야 실기와 대조되는지를
알아야 등급을 매기고 · 항목을 고르고 · 한계를 특정할 수 있다. 도구만 다루는 쪽에서는 나오지 않는다.

### ① 신뢰 등급을 함께 준다

결론만 주지 않는다. **그 결론이 어떤 값 위에 서 있는지**를 등급으로 표시한다.

| 등급          | 뜻                               |
| ------------- | -------------------------------- |
| **실측**      | 도면·실물에서 직접 잰 값         |
| **형상 산출** | 형상에서 역산한 값 (사양서 아님) |
| **추정**      | 동작하도록 고른 값               |
| **미확보**    | 사양서가 필요한 값               |

그래서 이런 문장이 산출물에 들어간다.

> "위치 제어 정확도에 대한 결론은 믿어도 된다. 그러나 **힘·토크·파지력에 관한 어떤 결론도 이 모델에서 끌어내면 안 된다** — 질량과 관성이 추정값이다."

이 한 문장이 고객을 잘못된 투자에서 구한다. **근거: 실제 프로젝트 기준 문서 §7 에서 쓰던 방식이다.**

### ② 차이를 숫자로 준다

"비슷하게 움직입니다"가 아니라 항목별 수치로 준다.

- 모델과 시뮬레이션의 기구학 차이
- 궤적 추종 오차 · 정착 후 잔류 오차
- 직선 이송의 경로 이탈량
- 주행 실효율(슬립)
- 시뮬레이터 실행 조건에 따른 정확도 변화

**숫자가 있어야 다음 바퀴에서 줄었는지 알 수 있다.** 이것이 정합(alignment)이라는 말의 실체다.

### ③ 한계를 먼저 선언한다

모델의 알려진 결함을 목록으로 넘긴다 — 미확보 사양, 특이 자세, 충돌체 누락, 축 이름 불일치 등. 숨기면 사고가 나고, 밝히면 신뢰가 된다.

## 6. 서비스 구성

파이프라인 위의 위치에 따라 다섯 단계로 나눈다. 앞 단계 없이 뒤 단계만 수행할 수도 있다.
**다섯 모두 고객의 개발을 대신하지 않는다** — 고객의 개발이 그 위에서 돌게 만드는 일이다(§1-1).

| #   | 서비스                     | 루프 위치        | 고객이 얻는 것                                 |
| --- | -------------------------- | ---------------- | ---------------------------------------------- |
| 01  | **제작 전 검토**           | 모델 구성        | 이 구성으로 그 작업이 되는지에 대한 답         |
| 02  | **작업 시나리오 검증**     | 시뮬레이션       | 실제 공정 순서가 도는 것과 그 사이클 타임      |
| 03  | **가상 시운전**            | 검증             | 제어 로직·인터록을 설치 전에 확인              |
| 04  | **Sim-to-Real 정합**       | 실기 → 차이 계측 | 시뮬레이션과 실물의 차이를 수치로, 그리고 좁힘 |
| 05  | **Physical AI 테스트베드** | 루프 전체 재사용 | 학습·평가에 쓸 수 있는 신뢰 등급이 매겨진 환경 |

**04 가 이 사업의 중심이다.** 01~03 만 하는 곳은 많지만, 실기까지 가서 차이를 재고 좁히는 곳은 드물다.

## 7. 산출물 (무엇을 받는가)

| 산출물              | 내용                                                      |
| ------------------- | --------------------------------------------------------- |
| 검증 리포트         | 항목별 판정 + **각 결론의 신뢰 등급**                     |
| 물리·제어 기준 문서 | 모델에 들어간 모든 값과 그 출처 등급                      |
| 차이 계측표         | 시뮬레이션 ↔ 실기 항목별 수치                             |
| 알려진 한계 목록    | 미확보 사양, 구조적 실패 지점, 사용하면 안 되는 조건      |
| 재현 절차           | 같은 결과를 다시 만드는 방법 — 재현 못 하면 검증이 아니다 |
| 시뮬레이션 환경     | 인수인계 가능한 형태 (자산 · 설정 · 실행 스크립트)        |

## 8. 고객과 계약 형태

**고객**: 로봇 SI 기업 · 자동화 설비 기업 · 제조 기업 · AMR(Autonomous Mobile Robot) 및 로봇팔 제조사 · 연구기관

**들어오는 시점**:

| 시점              | 필요한 것                                    |
| ----------------- | -------------------------------------------- |
| 견적·제안 단계    | "이 구성으로 되는가" 빠른 판정               |
| 설계 확정 전      | 레이아웃·도달성·사이클 타임 검토             |
| 제작 중           | 제어 로직 사전 검증                          |
| 설치 후 문제 발생 | 원인 분리 — 게인인지 통신인지 구조인지       |
| 실기 보유         | 차이 계측과 정합, 이후 변경의 사전 검증 환경 |

**형태**: 건별 검토 → 프로젝트 단위 검증 → 정합 및 환경 인수인계. 상주·파견은 하지 않는다(§2).

## 8-1. 조직 — 규모의 단위가 바뀌었다

옛 전제는 **사람 수가 처리량을 정한다**였다. 그래서 1인 스튜디오는 큰 일을 받을 수 없다고 여겨졌다.

지금 처리량을 정하는 것은 **지능의 규모**다. 사람 한 명과 여러 에이전트가 함께 일하고,
병목은 손이 아니라 **판단이 닿는 범위**에 있다.

| 사람이 정한다                         | 에이전트가 맡는다                   |
| ------------------------------------- | ----------------------------------- |
| 무엇을 재야 답이 나오는가 (질문 설계) | 조사 · 근거 수집 · 문서 대조        |
| 어떤 값을 믿을 수 있는가 (신뢰 등급)  | 자산 변환 · 환경 구성 · 반복 실행   |
| 무엇을 결론으로 넘길 것인가           | 계측 · 회귀 · 기록 · 재현 절차 정리 |
| 어디까지가 이 모델의 한계인가         | 전후 비교표 · 변경 이력 유지        |

### 이 구조가 성립하는 조건

**에이전트가 만든 것도 계측으로 확인되기 전에는 결론이 되지 않는다.**
이 사업이 고객에게 요구하는 기준(§5 신뢰 등급)을 자기 작업에도 그대로 적용한다는 뜻이다.
스스로 만든 것을 스스로 승인하지 않고, 재현 절차가 남지 않은 산출물은 산출물로 치지 않는다.

이 조건이 빠지면 지능의 규모는 **빠르게 틀리는 능력**이 된다.

### 고객에게 뜻하는 것

- 견적의 단위가 인시(人時)가 아니라 **판단과 산출물**이다(§2 · §8과 같은 이유).
- 사람 수로 물량을 대는 대신, 한 사람의 판단이 커버하는 폭을 넓혀 대응한다.
- **못 하는 것은 그대로 못 한다** — 현장 상주, 여러 사이트 동시 실기 대응처럼
  물리적 임장이 필요한 일은 이 구조로 늘어나지 않는다(§2).

## 9. 이 사업이 실패하는 방향

1. **신뢰 등급 없이 결론만 파는 순간** — 일반 시뮬레이션 용역과 구분이 사라진다.
2. **루프가 끊기는 순간** — 실기까지 안 가면 04 가 없어지고 차별점이 사라진다.
3. **인시를 파는 순간** — 파견 업으로 되돌아간다. 이 사업을 시작한 이유가 없어진다.
4. **로봇 개발을 대신 하기 시작하는 순간** — 고객의 개발 주체성을 가져오면 우리는 병목이 되고,
   파이프라인을 파는 대신 손을 파는 일로 미끄러진다(§1-1).
5. **에이전트 산출물을 검증 없이 넘기는 순간** — 지능의 규모(§8-1)가 빠르게 틀리는 능력으로 바뀐다.
   자기 작업에 자기 기준을 적용하지 못하면 §5 를 팔 자격이 없다.
6. **못 하는 것을 판다고 하는 순간** — 학습 정책 개발은 현재 [조사] 단계다. 첫 실적 전까지 환경 구축까지만 판다.
